01

As duas direções

Uma integração com o n8n tem duas pernas. O CRM já resolveu a primeira; a segunda ainda não existe.

Mensagem chega worker WhatsApp
CRM grava e dispara webhook-dispatch.ts
n8n recebe o evento POST autenticado

Implementado  saída — o CRM chama o n8n.

Agente decide a resposta n8n / IA
POST /api/v1/mensagens Bearer sk_live_…
WhatsApp entrega via worker

Implementado  volta — o n8n chama o CRM para enviar. Ver §08.

02

Quando o webhook dispara

O gatilho fica em commitMessage, o mesmo ponto que já aciona as automações internas do CRM — logo depois da mensagem ser gravada, nunca antes. Só mensagem recebida dispara; o eco do que a própria empresa envia não gera evento, senão uma resposta automática acabaria reagindo a si mesma.

EventoDispara quandoStatus
conversa.criada A mensagem recebida é a primeira da conversa Implementado
mensagem.recebida A mensagem chega numa conversa que já existia Implementado
conversa.resolvida Um atendente marca a conversa como resolvida Sem gancho
contato.criado Um contato novo é cadastrado Sem gancho

Como inscrever

Configurações → Integrações → novo webhook. A URL do n8n e os eventos marcados ficam salvos por conta; cada evento só chega a quem o marcou.

De onde cada campo vem

Para quem já conhece o payload cru de uma Evolution API / Baileys: o de-para do que o workflow real consultava.

data.key.id→mensagem.externalId
data.key.remoteJid / remoteJidAlt→contato.jid
data.key.fromMe→mensagem.deMim
data.pushName→contato.nome
data.messageType→mensagem.tipo
data.messageTimestamp→mensagem.recebidaEm
data.message.conversation / extendedTextMessage→mensagem.texto
chatwootConversationId→conversa.id
contextInfo.externalAdReply→nada — ver §05

remoteJidAlt e participant existem no protocolo cru para resolver o endereçamento LID→telefone e identificar quem falou dentro de um grupo. O CRM já resolve isso no servidor — é por isso que contato.telefone chega pronto em E.164, sem o fluxo precisar entender LID.

05

Contexto de anúncio Implementado

Por que este bloco importa

Quando um cliente clica num anúncio do Instagram/Facebook e cai direto no WhatsApp, a primeira mensagem carrega um bloco contextInfo.externalAdReply — título, corpo e link do anúncio, mais um ctwaClid que identifica o clique. O workflow analisado usa isso pesadamente: é o que permite ao agente responder já sabendo qual tratamento o paciente quer, sem perguntar de novo.

O CRM agora lê esse bloco nos dois motores, no ponto em que a mensagem crua ainda existe, e o entrega como anuncio — no primeiro nível do payload, ao lado de mensagem.

presente só na mensagem que veio do clique
{
  "evento": "conversa.criada",
  "...": "...",
  "anuncio": {
    "titulo": "Fechamento de diastema",
    "conteudo": "Feche o espaço entre os dentes",
    "clickId": "AbC123xyz",
    "link": "https://instagram.com/anuncio"
  },
  "mensagem": {
    "tipo": "text",
    "texto": "Olá, posso ter mais informações sobre isso?",
    "...": "..."
  }
}
CampoTipoSempre?Descrição
titulostringsimTítulo do anúncio. Pode vir vazio se o anúncio não tiver.
conteudostringsimCorpo do anúncio, já limpo — o WhatsApp cola o próprio número e o link no fim, e isso é removido antes de entregar.
clickIdstringnãoIdentificador do clique (ctwaClid, ou sourceId quando aquele falta). Serve para não tratar o mesmo clique duas vezes.
linkstringnãoURL de origem do anúncio.

Três detalhes de comportamento

O bloco é procurado em três lugares — texto estendido, imagem e vídeo — porque muda de posição conforme o tipo da mensagem; procurar num só perderia os outros silenciosamente. Um externalAdReply presente mas inteiramente vazio é descartado como ruído de protocolo, em vez de virar um "clique" falso. E o campo só aparece no que o contato enviou: o eco das mensagens da própria empresa carrega o mesmo bloco e não significa clique nenhum.

06

Autenticação Implementado

Se o webhook tiver uma chave de verificação cadastrada, toda entrega leva uma assinatura HMAC-SHA256 — o mesmo formato que n8n, Make e Zapier já sabem conferir nativamente. O campo fica na própria tela de cadastro do webhook, em Configurações → Integrações.

CabeçalhoSempre?Valor
Content-Typesimapplication/json
X-Solint-EventsimO nome do evento, ex. mensagem.recebida
X-Solint-Signaturesó com segredo cadastradosha256=<hex>
User-AgentsimSolint-CRM-Webhook/1

Conferindo no n8n

Code node · JavaScript
const crypto = require('crypto');
const segredo = 'SEU_SEGREDO_CADASTRADO_NO_CRM';

const corpoRecebido = JSON.stringify($input.first().json.body);
const assinaturaRecebida = $input.first().json.headers['x-solint-signature'];

const esperada = 'sha256=' +
  crypto.createHmac('sha256', segredo).update(corpoRecebido).digest('hex');

if (assinaturaRecebida !== esperada) {
  throw new Error('Assinatura não confere — descarte esta requisição.');
}

return $input.all();

Nota

A assinatura é calculada sobre os bytes exatos do corpo. Se o node Webhook do n8n já reserializou o JSON antes de chegar ao seu Code node, a comparação pode falhar por diferença de formatação — não pelo segredo estar errado. Vale checar a opção de corpo bruto (raw body) do node de entrada se a verificação não bater.

07

Baixar mídia Implementado

midia.caminho nunca foi um link aberto, e continua não sendo: é conteúdo de conversa de cliente, protegido por escopo de conta. O que mudou é que a rota passou a aceitar duas portas — o cookie do navegador e um token de API. Um fluxo que precise transcrever um áudio ou analisar uma imagem agora consegue buscar os bytes.

GET /api/whatsapp/media/{id}midia.caminho vem pronto no payload
GET https://seu-crm.com/api/whatsapp/media/AC7CFA2B6CACAAC59011534B0202BD5E
Authorization: Bearer sk_live_xxxxxxxxxxxxxxxx

→ 200  os bytes, com Content-Type e Content-Disposition corretos
→ 401  token ausente, inválido ou expirado
→ 404  mídia inexistente — ou de outra conta

Por que 404 e não 403 para mídia de outra conta

Responder 403 confirmaria que aquele id existe em algum lugar do sistema. Se a mídia não é sua, se ela existe ou não é informação que também não lhe pertence.

Onde criar o token

Configurações → Integrações → Tokens de API. O segredo (sk_live_…) aparece uma única vez, no momento da criação: o banco guarda apenas o SHA-256 dele. Um token perdido não se recupera, se substitui.

Nenhuma regra de negócio mora nesta rota

Ela autentica, valida a entrada e chama exatamente o mesmo caso de uso que o formulário da tela chama — que é quem confere a permissão, a janela de 24h e o limite de tamanho. Duplicar essas regras aqui criaria dois lugares para elas divergirem.

Respostas possíveis

StatusQuandoCorpo
200 Aceito. entregue: true quando o canal já confirmou; enfileirado: true quando o worker aceitou mas ainda não entregou { "ok": true, "mensagemId": "…", "entregue": true }
400 Corpo inválido, texto vazio ou acima de 4096 caracteres { "ok": false, "erro": "…" }
401 Token ausente, inválido ou expirado { "ok": false, "erro": "…" }
403 O token não tem a permissão conversas:responder { "ok": false, "erro": "…" }
404 conversaId não existe ou não pertence à conta do token { "ok": false, "erro": "…" }
409 Janela de 24h fechada — sem template aprovado, o WhatsApp recusa { "ok": false, "erro": "…" }
503 WhatsApp desconectado. A mensagem já foi gravada — o mensagemId vem junto { "ok": false, "mensagemId": "…", "erro": "…" }

Uma decisão que vale conhecer

No 503, a mensagem não é desfeita. Ela já está gravada e visível na timeline com estado de falha. Apagá-la faria o histórico da tela divergir do que quem integra viu acontecer — e o mensagemId vem na resposta justamente para o fluxo poder acompanhá-la.

09

O que ainda falta

Dois eventos já aparecem na tela de integrações e podem ser marcados, mas nenhum ponto do código os dispara ainda. É a única lacuna que resta na integração.

EventoDispararia quandoOnde o gancho entraria
conversa.resolvida Um atendente marca a conversa como resolvida na tela Server Action que muda o status da conversa
contato.criado Um contato novo entra no CRM — pelo WhatsApp ou cadastro manual upsertContact, no caminho que grava um contato pela primeira vez

10

Checklist para adaptar o fluxo

  • Trocar o webhook de entrada Do node Evolution API para o webhook do CRM. Os campos que o fluxo já usa para texto, tipo, nome e telefone têm equivalente direto — ver §03.
  • Criar um token de API Configurações → Integrações → Tokens de API. O segredo aparece uma única vez. É o mesmo token para baixar mídia e para enviar resposta.
  • Cadastrar o webhook com chave de verificação URL do n8n, os eventos desejados e uma chave de no mínimo 16 caracteres. Valide X-Solint-Signature antes de processar qualquer evento — ver §06.
  • Ler o contexto de anúncio do bloco anuncio O bloco [CONTEXTO DO ANÚNCIO] do prompt passa a ser montado a partir de anuncio.titulo e anuncio.conteudo — ver §05. Use anuncio.clickId para não tratar o mesmo clique duas vezes.
  • Trocar o download de mídia Aponte o node HTTP para midia.caminho com o header Authorization: Bearer — ver §07. Substitui a chamada getBase64FromMediaMessage do fluxo atual.
  • Trocar o envio de resposta POST /api/v1/mensagens no lugar de sendText da Evolution API — ver §08. Ganha de brinde o registro na timeline do CRM, que a chamada direta não fazia.
